# v0.3 Product Audit — Import → Build → Show → Live

This replaces the feature-shaped sidebar as the primary mental model. The app has four operator workspaces. Settings/diagnostics remain secondary.

## 1. Import

Purpose: create a durable Song asset.

- New/Open Studio Show
- Add Song
- Import WAV/MP3/AIFF/stems
- optional stem split
- BPM/downbeat/key analysis
- map/relink media
- replace pad samples
- attach video
- choose MIDI resources
- create or recall the song's LumaRig lighting show

Exit condition: the Song is playable and every referenced asset has a health state.

## 2. Build

Purpose: program one Song.

- Arrangement and sections
- real audio tracks and buses
- mixer controls
- pads
- MIDI cues
- video clips + display/NDI routing
- lighting programming through LumaRig
- record/replay LumaRig lighting takes
- section cue assignment
- Link/sync configuration

All editing surfaces operate on the same Song model. No duplicate state.

## 3. Show

Purpose: assemble and rehearse the Studio Show.

- ordered setlist
- song readiness
- transitions
- global output routing
- LumaRig show bindings
- NDI/display destinations
- MIDI devices
- Ableton Link session
- preflight and missing-media checks

A Studio Show contains Song references. A Song keeps a stable ID so its lighting programming can be recalled in another Studio Show.

## 4. Live

Purpose: perform with protected controls.

- current/next song
- current/next section
- GO / previous / stop
- transport
- essential mixer
- pads
- lighting status/manual override
- video/NDI status
- Link peer/tempo status
- emergency blackout

Editing operations are hidden or guarded.

# LumaRig integration

LumaRig remains lighting authority. Studio never writes raw DMX.

## Identity

Studio sends:
- studioShowId
- studioShowName
- songId
- songTitle
- songBpm

LumaRig persists a binding:
`studioShowId + songId -> lumarigShowId`

It also maintains a reusable Song binding:
`songId -> preferredLumaRigShowId`

When the same Song is inserted into another Studio Show, Studio offers the existing lighting show rather than silently creating a duplicate.

## Connection order

1. Same-device local endpoint: discover a running LumaRig instance and connect over loopback.
2. LAN discovery: discover LumaRig peers and connect to its direct local WebSocket service.
3. Network Session: authenticated relay for different networks.
4. MIDI remains an interoperability/fallback path, not Studio's semantic control protocol.

The existing LumaRig Supabase relay protocol already has revisioned snapshots, semantic commands, heartbeat and command results. The direct endpoint should carry the same envelopes so local and remote connections are transport variants, not separate APIs.

## Programming flow

Opening Lighting in Build:
1. Resolve the Song binding.
2. If absent, Studio asks LumaRig to create a show named from the Song and Studio Show.
3. LumaRig returns stable show ID.
4. Studio stores the binding.
5. Program fixtures/cues/FX in LumaRig using its ShowRuntime.
6. Record Show captures the existing 20 Hz changed-DMX take in LumaRig.
7. Studio stores only semantic references: show ID, cue/scene/take IDs and timing.
8. Playback dispatches those references at master-transport section/timeline boundaries.

This preserves LumaRig's one-source-of-truth rule and makes existing recorder, cues, FX, fixture profiles and physical output reusable.

## Ableton Link

Link is sync, not absolute song-position ownership. Studio's audio transport remains authoritative for its arrangement. Link supplies shared tempo/beat/phase and optional start/stop intent. Quantized launches align to Link quantum. Do not run Link and MIDI Clock as competing tempo masters.

# Control audit rule

Every visible interactive element must be one of:
- FUNCTIONAL: mutates/queries the real runtime.
- DISABLED: visibly disabled with a reason.
- NAVIGATION: opens a real workspace/dialog.

No fake knobs, faders, switches, search fields, meters, connection buttons or transport controls ship in v0.3.

Known v0.2 gaps found in audit:
- remote pad.trigger / pad.release explicitly reject as not wired
- remote lighting.blackout / lighting.scene / lighting.xy explicitly reject as not wired
- MIDI page is informational UtilityPage
- Video page is informational UtilityPage
- Songs search input is decorative
- YouTube reference input is decorative
- several demoSetlist-backed surfaces are not persistent project state

These are blockers for v0.3 Functional Core.
